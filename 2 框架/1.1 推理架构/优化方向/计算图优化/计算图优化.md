# 计算图优化

一句话定位：**eager 是"写一行跑一行"，graph 是"先看清整张图再动手"**。vLLM/SGLang 默认开 CUDA Graph、可选 torch.compile，吃的就是计算图这套红利。本文回答四个问题：图是什么 → 优化/编译/缓存的关系 → 为什么需要图优化 → 黑话速查。

# 计算图是什么：Eager vs Graph 模式

计算图 = **节点是算子、边是张量依赖关系的 DAG**。它把"程序想算什么"（图，可分析可变换）和"具体怎么执行"（kernel 调用）解耦开。

**Eager（动态图）模式**：PyTorch 默认。Python 解释器逐行执行，每个算子立即发射到 GPU、算完即返回，框架永远不知道下一个算子是什么。

**Graph（静态图）模式**：先捕获代码生成图（不执行），在图上做优化和编译，最后整图执行。

```
Eager：边解释边执行，算子逐个发射
  y = relu(linear(x));  z = layernorm(y)
        │         │          │
        ▼         ▼          ▼
     dispatch   launch     launch        ← 每个算子独立：Python开销 + launch + 中间结果落 HBM
     [Linear] ─▶ [ReLU] ─▶ [LayerNorm]
     x ─(HBM)─▶ h ─(HBM)─▶ y ─(HBM)─▶ z  ← 中间结果必须写回显存、再被下个 kernel 读出

Graph：先捕获成图 → 优化 → 编译 → 整体执行
  ①捕获  y=relu(linear(x))    ─▶   (linear)─▶(relu)─▶(norm)     节点=算子, 边=张量
  ②优化  发现 linear+relu 可合 ─▶   (linear_relu)──▶(norm)       图上重写，还没生成任何代码
  ③编译  生成/挑选 kernel      ─▶   [Triton kernel A][kernel B]  autotune 选优后的产物
  ④执行  整图一次调度（还可再被 CUDA Graph 捕获，之后单次 launch 回放）
```



| 维度 | Eager（动态图） | Graph（静态图） |
| :--- | :--- | :--- |
| 执行时机 | 写到哪行执行到哪行 | 先构图 → 优化 → 编译 → 执行 |
| 全局视野 | 无，逐算子调度 | 有，可融合/重排/内存规划 |
| 中间结果 | 全部落 HBM | 融合后可留在寄存器/共享内存 |
| 动态控制流 | 天然支持 | 需 capture + guard，条件变化触发重编译 |
| 调试 | print/断点随便打 | 图内是黑盒，要靠专用工具 |
| 代表 | PyTorch 默认模式 | torch.compile、TF 1.x/XLA、JAX (jit) |

# 计算图优化 vs 图编译 vs 缓存：三者的关系

三者不是并列的三种技术，而是**同一条编译流水线上的三层**（以 torch.compile 栈为例）：

```
 nn.Module（PyTorch 代码）
      │ ① 捕获：TorchDynamo 分析字节码 → FX Graph + Guards
      │    （guard = 这张图成立的条件，如 shape/dtype；条件变了就重新捕获）
      ▼
┌────────────────────────────────────────────────┐
│ ② 计算图优化（前端）：图级重写，快，硬件无关        │
│    算子融合 / 常量折叠 / CSE / 布局变换 / 死代码消除 │
│    → 只改"图的结构"，产物仍是一张图               │
└────────────────────────────────────────────────┘
      ▼ ③ 图编译（后端）：lowering，慢，硬件强相关
┌────────────────────────────────────────────────┐
│  TorchInductor：图 → IR → autotune → codegen     │
│    → 产物是可执行的东西：Triton kernel / CUDA 代码 │
└────────────────────────────────────────────────┘
      ▼ ④ 缓存（按 Cache Key 复用，横跨②③）
┌────────────────────────────────────────────────┐
│  FX graph cache / Inductor cache / 编译好的产物    │
│  Key 相同 → 直接复用，整段跳过②③                  │
└────────────────────────────────────────────────┘
      ▼
  运行时：CUDA Graph 捕获 launch 序列，回放时一次提交  ← 执行层面的"缓存"
```

三层各自回答的问题：

| 层 | 回答的问题 | 干什么 | 代价 |
| :--- | :--- | :--- | :--- |
| **计算图优化** | 算什么、怎么组织 | 图上做模式匹配与重写（融合、折叠、消除） | 秒级，纯图变换 |
| **图编译** | 用哪个 kernel、怎么算 | lowering + autotune + codegen 生成代码 | 分钟级，要真跑 benchmark |
| **缓存** | 要不要重做 | 用 Cache Key 复用编译产物；CUDA Graph 复用执行序列 | 首次付清，之后零成本 |

类比记忆：**优化 = 改菜谱**（把三道工序合并成一道），**编译 = 把菜谱翻译成这台灶台的具体操作**（火候顺序实测调优），**缓存 = 菜谱和半成品存档**（同样订单再来了直接开工）。

LLM 推理的落地：vLLM/SGLang 的 `--enable-torch-compile` + 默认开启的 CUDA Graph 就是这条流水线。编译发生在**启动 warmup 阶段**，服务期全靠缓存命中，所以编译慢不影响稳态性能——除非 shape 频繁变化把缓存打穿，造成 recompile 风暴。

# 为什么需要图优化：Eager 模式的三大痛点

**痛点 1：Kernel Launch 开销（CPU 成瓶颈）**

- 从 host 发射一个 kernel 约 5~10 μs，eager 下每个算子一次 launch，外面还包着 Python 解释 + dispatcher 派发；
- **decode 阶段是重灾区**：batch 小、kernel 多而碎，单个 kernel 真正计算只有几 μs，launch 开销 1:1 陪跑 → GPU 在等 CPU（GPU starvation）；
- 一个 decode step 几百上千个 kernel，纯 launch 开销就到毫秒级，而单步预算（ITL）本身只有 10 ms 量级。

**痛点 2：显存读写（带宽是 LLM 推理第一瓶颈）**

- LLM 推理是 memory-bound：耗时 ≈ 搬运字节数 / 带宽；
- eager 每个算子独立成 kernel，中间结果必须**写回 HBM → 再被下一个 kernel 读出**，一来一回白搬两次；
- 融合后中间结果留在寄存器/共享内存，这两趟全免。RMSNorm、reshape、silu 这类细碎算子是典型受益者——eager 下是"访存大户、计算贫农"。

**痛点 3：无法全局调度（看不见整图，什么都做不了）**

- **不能融合**：算完一个才知道下一个，没有全局模式匹配的机会；
- **不能重排**：无法交换/并行无依赖分支，无法把只依赖常量的子图提前算掉（constant folding）；
- **不能规划显存**：无法做 buffer 生命周期分析（用完即复用）、in-place 决策；
- **不能特化**：eager kernel 必须适配任意 shape；图模式下静态 shape 可以生成特化 kernel（展开循环、常量索引、更激进的向量化）。

公平地说，eager 的灵活（随时 print、任意动态控制流）正是 PyTorch 统治科研的原因。所以 graph 模式不是替代而是共存——Dynamo 用 **capture + guard + recompile** 换取"eager 的灵活 + graph 的性能"：shape 稳定时命中缓存零开销，条件变了就回退 eager 或重编译。

# 关键术语表（一句话版）

| 术语 | 一句话解释 |
| :--- | :--- |
| 计算图 | 节点=算子、边=张量依赖的 DAG，一切优化的载体 |
| Eager 模式 | 立即执行：Python 写一行跑一行，框架看不到全局 |
| Graph 模式 | 先捕获成图，再整体优化、编译、执行 |
| TorchDynamo | torch.compile 的前端，从字节码捕获生成 FX Graph 并挂 guard |
| FX Graph | PyTorch 的算子级中间表示（function 语义的 DAG），Dynamo 的输出 |
| IR | 中间表示，编译各阶段操作的载体（FX → Inductor IR → Triton IR），一层层逼近硬件 |
| Pass | 对图/IR 做一次"遍历+变换"的最小优化单元（fusion pass、CSE pass），优化 = 一串 pass 串起来 |
| Lowering | 从高层 IR 降级到更贴近硬件的表示（算子语义 → 循环/内存访问） |
| Fusion（算子融合） | 把多个小 kernel 合成一个，既省 launch 也省中间结果的显存往返 |
| Constant Folding | 编译期把只依赖常量的子图直接算掉（如 RoPE 的 cos/sin 表预计算） |
| CSE | 公共子表达式消除，相同的计算只算一次 |
| Codegen | 从 IR 生成目标代码（Triton / CUDA C++ / LLVM） |
| Autotune | 同一算子试多组调度参数（block size、num_warps…）实测选最快 |
| Cache Key | 唯一标识一次编译输入的指纹（图结构 + shape + dtype + 参数版本 + 硬件 + 编译器版本），命中即复用产物 |
| Guard | 捕获时记录的运行时条件（shape/dtype/属性），每次执行先验一遍，失效则 recompile |
| Recompile（编译风暴） | shape 频繁变化导致缓存永不命中、反复重编译；LLM 推理用 padding-to-bucket 收敛 shape 种类来规避 |
| CUDA Graph | 运行时捕获一段 kernel launch 序列，之后一次 launch 整段回放——执行层面的缓存 |
| TorchInductor | torch.compile 默认后端：FX Graph → 融合 → 生成 Triton（GPU）/ C++（CPU） |
| Symbolic Shape（动态 shape） | 用符号变量（s0, s1）表示维度，一张图服务多个具体 shape，减少 recompile |
| AOT vs JIT | 提前编译（启动时全编好）vs 运行时按需编译（首次触达才编） |
