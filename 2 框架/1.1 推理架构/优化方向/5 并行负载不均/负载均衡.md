# 负载均衡

> 并行策略的原理与通信代价见 [5P 推理](../../推理并行/5p推理.md)。并行切分都默认"负载均匀"，但真实负载（请求长度分布、专家热度、stage 计算量）天然不均匀——**不均衡的卡就是长尾的源头**：快卡全部在栅栏处等最慢的卡。
>
> **定位（横切关注点）**：本文横跨两层均衡——**布局层**（PP stage 切分 / EP 专家放置，部署期静态确定）与**调度层**（DP 请求派发，运行期动态进行）。调度层的完整机制（batch 攒批、PD 配比）见 [服务吞吐与调度](../服务吞吐与调度/pd.md)，本文只讲"均衡"这一刀。

## 为什么并行后必然不均衡

| 并行维度 | 不均衡来源 | 后果 |
| --- | --- | --- |
| PP | 各 stage 层数/计算量不等，embedding 与 lm_head 重量偏向首尾 | 慢 stage 拖整条流水线，气泡变大 |
| EP | 动态路由 → 热门 expert 堆到同一 rank | A2A 栅栏处全员等最忙的卡 |
| DP | 请求按 rank 绑定，长度/到达率波动 | 冷热不均，慢 rank 独自排队 |
| TP | 切分基本均匀；KV head 不整除时需复制 | 影响较小，主要是显存放大 |

## 各维度对策

### PP：stage 切分均衡

- 按**每层 FLOPs + 显存占用**搜索切分边界，让各 stage 耗时接近
- embedding / lm_head 的额外开销计入首尾 stage 再平衡
- 残余气泡用 micro-batch 摊平：`bubble_ratio = (P-1)/(M+P-1)`

### EP：专家负载均衡（最重头）

MoE 的 router 是"请求决定负载"，切分时无法预知热度，均衡要靠运行期机制：

- **capacity factor**：给每个 expert 预留超额容量（如 1.25×），超出部分丢弃或溢出——简单但浪费/有损
- **EPLB（Expert Parallel Load Balancer，DeepSeek）**：
  - 统计线上专家热度（expert distribution recorder）
  - 把**热门专家冗余复制**到多卡（redundant experts），冷门专家合并到同卡
  - 分层版本：先均衡卡间（全局），再均衡节点内（同卡复制避免跨节点），与冗余度、组大小联合求解
- **训练侧**：auxiliary load-balancing loss / 无 aux loss 的均衡（DeepSeek-V3 用 seq-level 辅助损失），属于训练范畴，这里只作衔接

### DP：请求级负载均衡

- LB 指标与阶段强相关：prefill 看计算时长 / decode 看 KV 占用与队列深度，两者分布不同 → 分阶段统计
- vLLM 内置 dp dispatcher（`DPLBAsyncMPClient`），`data_parallel_external_lb` 时交给外部 LB（网关/前端调度）
- 极端形态是 **PD 分离**：prefill 与 decode 容量各自规划、独立扩缩——详见 [PD 分离](../服务吞吐与调度/pd.md)

### TP：基本均匀

权重按维均分，无路由依赖，均衡的主要约束是 KV head 整除（否则复制放大 KV cache）。

## 与其他优化的关系

- **集群通信优化**：不均衡直接放大通信栅栏（EP 的 A2A 等最慢 rank），解法见 [集群通信优化](../集群通信优化/集群通信优化.md)
- **服务吞吐与调度**：DP 层面的均衡本质是调度问题（把请求派给谁），见 [服务吞吐与调度](../服务吞吐与调度/pd.md)
- **显存优化**：EPLB 复制专家是"用显存换均衡"，与 offload 抢同一份显存预算，见 [显存优化与offload](../显存优化与offload/显存优化与offload.md)
